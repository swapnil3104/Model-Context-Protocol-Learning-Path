# 1. Introduction

Logging is the practice of recording information about what an application is doing.

For MCP systems, logging is useful for understanding:

```text
What happened?
When did it happen?
Which component produced it?
Which request caused it?
Did the operation succeed?
Why did it fail?
How long did it take?
What should an operator investigate?
```

A simplified MCP system may contain:

```text
User
  |
  v
MCP Host
  |
  v
MCP Client
  |
  v
MCP Server
  |
  +---- Tools
  |
  +---- Resources
  |
  +---- Prompts
  |
  +---- External APIs
```

Logs provide visibility into this system.

---

# 2. Important Version Note

MCP Logging has an important specification-version distinction.

The MCP specification revision **2026-07-28** formally deprecated the protocol-level Logging feature. The feature continues to exist for compatibility during the deprecation period, but new implementations are advised not to build new systems around it. The official MCP release notes identify `stderr` for stdio transports and OpenTelemetry for structured observability as the modern direction. citeturn0search2turn0search3

Therefore, this module teaches Logging for two reasons:

```text
1. Understand existing MCP implementations
2. Understand general production logging and observability
```

For modern projects, prefer:

```text
Application Logging
        +
stderr for stdio servers
        +
Structured Logging
        +
OpenTelemetry
        +
Centralized Observability
```

rather than designing a new application around the deprecated protocol-level Logging capability. The current Python SDK documentation explicitly says the protocol-level Logging capability is deprecated and recommends ordinary standard-library logging instead. citeturn0search1

# 3. What is Logging?

Logging means recording events generated by a software system.

Example:

```text
2026-08-10 10:15:22 INFO Starting MCP server
2026-08-10 10:15:24 INFO Tool called: search_books
2026-08-10 10:15:25 INFO Tool completed
```

A log record usually contains:

```text
Timestamp
Level
Logger Name
Message
Context
```

A structured record may contain:

```json
{
  "timestamp": "2026-08-10T10:15:22Z",
  "level": "INFO",
  "logger": "bookshop",
  "message": "Tool execution completed",
  "tool": "search_books"
}
```

Logging helps developers and operators:

### Debug

### Troubleshoot

### Monitor

Observe application behavior.

### Audit

Record important operational events.

### Analyze Performance

Measure slow operations.

### Security

Identify suspicious activity.

### Reliability

Detect repeated failures.

# 5. Logging vs Application Output

Logging is different from returning data to the user or model.

For example:

```python
logger.info("Searching books")
return "Found 3 books"
```

The log is operational information.

The returned value is application output.

Conceptually:

```text
logger.info(...)
      |
      v
Operator / Log System


return ...
      |
      v
MCP Result / Application Consumer
```

The MCP Python SDK documentation explicitly emphasizes this distinction: a server log line is not automatically returned as tool output; if the model should receive information, the server should return that information as application data. citeturn0search1

# 10. Log Messages

A log message communicates an event.

Example:

```text
INFO: Tool search_books started
```

A useful log message should answer:

```text
What happened?
```

A better log:

```text
INFO search_books started query="mcp"
```

An even better structured event:

```json
{
  "level": "INFO",
  "event": "tool_started",
  "tool": "search_books",
  "query": "mcp"
}
```

Avoid vague messages such as:

```text
Something happened
Error occurred
Done
Problem
```

# 11. Logging Levels

Logging levels indicate the severity or importance of a log message.

Historical MCP logging follows severity concepts based on RFC 5424.

The levels are:

```text
DEBUG
INFO
NOTICE
WARNING
ERROR
CRITICAL
ALERT
EMERGENCY
```

They progress from low severity to high severity.

Conceptually:

```text
DEBUG
  ↓
INFO
  ↓
NOTICE
  ↓
WARNING
  ↓
ERROR
  ↓
CRITICAL
  ↓
ALERT
  ↓
EMERGENCY
```

The MCP C# SDK documentation describes these levels as the MCP logging levels and maps them to standard .NET logging abstractions. citeturn0search7

---

# 12. RFC 5424 Severity Levels

RFC 5424 defines standard syslog severity levels.

The conceptual order is:

| Level | Severity | Typical Meaning |
|---|---:|---|
| DEBUG | 7 | Detailed diagnostic information |
| INFO | 6 | Normal informational event |
| NOTICE | 5 | Normal but significant event |
| WARNING | 4 | Warning condition |
| ERROR | 3 | Error condition |
| CRITICAL | 2 | Critical condition |
| ALERT | 1 | Immediate action required |
| EMERGENCY | 0 | System unusable |

Lower numerical values represent higher severity.

---

# 13. Debug Logging

`DEBUG` is used for detailed diagnostic information.

Example:

```text
DEBUG Loading configuration file
DEBUG Preparing tool arguments
DEBUG Sending request to downstream API
DEBUG Response received
```

Debug logs are useful during development.

Avoid enabling very verbose debug logging permanently in production.

---

# 14. Info Logging

`INFO` represents normal operational activity.

Examples:

```text
INFO MCP server started
INFO Tool execution started
INFO Resource loaded
INFO Request completed
```

Information logs are commonly enabled in production.

---

# 15. Notice Logging

`NOTICE` represents a significant but normal event.

Examples:

```text
NOTICE Configuration changed
NOTICE Server entered maintenance mode
NOTICE Authentication policy updated
```

Not every logging framework exposes a separate Notice level, so applications may map it to another supported level.

---

# 16. Warning Logging

`WARNING` indicates something unusual that does not necessarily mean failure.

Examples:

```text
WARNING External API response is slow
WARNING Configuration uses deprecated option
WARNING Retry attempt 2 of 3
```

Warnings should not be used for ordinary successful operations.

---

# 17. Error Logging

`ERROR` indicates that an operation failed.

Examples:

```text
ERROR Database query failed
ERROR Tool execution failed
ERROR Invalid external API response
```

A useful error log should contain context.

Bad:

```text
ERROR Something failed
```

Better:

```text
ERROR search_books failed
      database_timeout=true
      duration_ms=5000
```

---

# 18. Critical Logging

`CRITICAL` indicates a severe failure affecting an important component.

Example:

```text
CRITICAL Database connection pool unavailable
```

Critical events may require immediate investigation.

---

# 19. Alert Logging

`ALERT` indicates that immediate action is required.

Example:

```text
ALERT Certificate expires in less than one hour
```

The exact operational meaning depends on the system.

---

# 20. Emergency Logging

`EMERGENCY` represents the highest severity.

It indicates that the system is unusable or facing an extremely serious condition.

Example:

```text
EMERGENCY MCP service unavailable
```

Use this level very carefully.

# 23. Logging Level Configuration

Historically, the client could request a minimum logging level using:

```text
logging/setLevel
```

Conceptual flow:

```text
Client
   |
   | Set minimum level = INFO
   v
Server
```

The server could then deliver messages at or above that threshold.

For example:

```text
Client level = INFO

DEBUG       → Filtered
INFO        → Sent
NOTICE      → Sent
WARNING     → Sent
ERROR       → Sent
CRITICAL    → Sent
ALERT       → Sent
EMERGENCY   → Sent
```

The historical C# SDK documentation describes `logging/setLevel` as the request used by clients to adjust the minimum severity sent by the server. citeturn0search6

# 24. Log Filtering

Filtering reduces unnecessary log traffic.

Example:

```text
Configured Level = WARNING
```

Then:

```text
DEBUG      ✗
INFO       ✗
NOTICE     ✗
WARNING    ✓
ERROR      ✓
CRITICAL   ✓
ALERT      ✓
EMERGENCY  ✓
```

This is useful when a client does not need detailed diagnostic information.

# 26. Stdio Logging

Stdio transport requires special care.

An MCP server using stdio communicates over standard input/output.

Conceptually:

```text
stdin
  |
  v
MCP Protocol

stdout
  |
  v
MCP Protocol
```

Therefore, application logging should not casually write arbitrary text to stdout because stdout is used by the protocol.

The MCP Python SDK documentation explicitly recommends standard logging and explains that stderr is the appropriate stream for server logs in stdio deployments. citeturn0search1

Use:

```python
logger.info("Server started")
```

rather than:

```python
print("Server started")
```

for normal server logging.

---

# 27. Streamable HTTP Logging

With Streamable HTTP, the server communicates using HTTP rather than a local stdin/stdout pipe.

Logging can therefore be handled through normal server-side logging infrastructure:

```text
MCP Server
    |
    v
Application Logger
    |
    v
stderr / File / Collector
    |
    v
Observability Platform
```

The exact delivery of protocol-level notifications depends on the MCP specification version and transport behavior.

For modern systems, structured observability is generally preferable to creating a new dependency on the deprecated Logging feature.

---

# 28. Structured Logging

Structured logging stores logs as machine-readable records.

Instead of:

```text
INFO Tool search_books completed in 120ms
```

use:

```json
{
  "level": "INFO",
  "event": "tool_completed",
  "tool": "search_books",
  "duration_ms": 120
}
```

Advantages:

```text
Easy Searching
Easy Filtering
Easy Aggregation
Easy Alerting
Machine Readability
Better Correlation
```

# 30. Protocol Logs

Protocol logs describe communication between components.

Examples:

```text

Response received
Connection established
Connection closed
Protocol error
Invalid message
Timeout
```

Protocol logging should avoid leaking sensitive content.

Instead of logging an entire request:



# 34. Request Correlation

A request ID allows related logs to be grouped.

Example:

```text
request_id = abc123
```

Logs:

```text
INFO request_id=abc123 request_started
INFO request_id=abc123 tool_started
INFO request_id=abc123 database_query
INFO request_id=abc123 tool_completed
```

Without correlation:

```text
request_started
tool_started
database_query
tool_completed
```

it may be difficult to know which events belong together.

# 38. Privacy and Sensitive Data

Never log secrets unnecessarily.

Avoid:

```text
API_KEY=sk-xxxxxxxx
PASSWORD=secret
TOKEN=abcdef
```

Avoid logging sensitive personal data unless required and permitted.

Instead:

```text
api_key_present=true
user_id_hash=...
payload_size=1024
```

Use redaction where appropriate.

---

# 39. Log Injection

Log injection occurs when untrusted input changes the appearance or meaning of logs.

Example:

```text
user_input = "hello\nERROR Authentication succeeded"
```

If logged directly, it may create misleading entries.

Safer approaches include:

```text
Structured Logging
Input Escaping
Sanitization
Length Limits
```

Structured JSON logging significantly reduces ambiguity.

# 44. Prompt Logging

Prompt-related logs should be handled carefully.

A useful log:

```text
INFO prompt_used
prompt=technical_support
```

Potentially risky:

```text

```

Prefer logging metadata:

```text

request_id
input_size
```

rather than full prompt contents.

# 45. Sampling and Logging

Sampling and Logging are separate concepts.

Sampling:

```text
Server
  ↓
Client
  ↓
Model
```

Logging:

```text
Application
  ↓
Logger
  ↓
Observability
```

A server can log that a sampling-related operation occurred without logging the complete model input.

Example:

```text
INFO sampling_request_started
request_id=abc123
```

rather than:

```text
INFO FULL_PROMPT=...
```

Because the protocol-level Sampling feature was also deprecated in the 2026-07-28 revision, new systems should prefer direct model-provider integrations where appropriate. citeturn0search2

# 51. Log Rotation

Large log files can consume disk space.

Log rotation can:

```text
Create New File
Archive Old File
Compress
Delete Expired Files
```

Conceptual flow:

```text
server.log
    |
    v

    |
    v

```

In containerized environments, logs are often emitted to stdout/stderr and collected by the runtime rather than manually managed as local files.

For stdio MCP servers, remember that stdout belongs to the protocol and stderr is the safer destination for operational logging. citeturn0search1

# 55. Python Logging

Python provides the standard `logging` module.

# 61. Common Mistakes

❌ Printing arbitrary text to stdout in a stdio MCP server.

❌ Logging passwords or API keys.

❌ Logging complete private documents.

❌ Using ERROR for normal events.

❌ Using DEBUG for everything.

❌ Logging without request IDs.

❌ Creating unstructured messages that are difficult to search.

❌ Logging every internal detail in production.

❌ Treating logs as user-facing output.

❌ Relying only on logs when traces or metrics are needed.

❌ Creating alerts for normal informational events.

❌ Keeping unlimited logs without a retention policy.

❌ Building a new application around the deprecated protocol-level MCP Logging feature.

# 62. Current MCP Logging Status

As of the **2026-07-28 MCP specification**, protocol-level Logging is deprecated. The release notes state that Roots, Sampling, and Logging were deprecated under the new feature lifecycle policy. The deprecation does not mean all existing implementations immediately stop working; the feature remains available during the compatibility period. citeturn0search2

The release candidate documentation describes the recommended direction for Logging as:

```text
Logging
   ↓
stderr for stdio transports

Structured observability
   ↓
OpenTelemetry
```

This is important when building a modern MCP learning repository.

# 64. Key Takeaways

- Logging records application and operational events.
- Logging is different from returning application data.
- MCP historically provided a protocol-level Logging capability.
- Historical MCP Logging used `notifications/message`.
- Historical clients could configure a minimum level with `logging/setLevel`.
- MCP logging levels follow RFC 5424 severity concepts.
- Logging levels range from DEBUG through EMERGENCY.
- Logging should be structured and searchable.
- Request IDs and trace IDs improve debugging.
- Sensitive data should not be logged unnecessarily.
- Stdio MCP servers should keep protocol output on stdout and operational logs on stderr.
- Logs, metrics, and traces provide complementary observability.
- OpenTelemetry is the modern direction for structured observability.
- Protocol-level MCP Logging was deprecated in the 2026-07-28 specification.
- Existing implementations may still support it for compatibility.
- New applications should generally use normal application logging and modern observability rather than depending on deprecated protocol-level Logging.
